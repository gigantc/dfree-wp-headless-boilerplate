# Block Folder Structure

This mirrors the sister PHP theme's block taxonomy exactly. When the same
mental model applies to both stacks, an editor's/dev's knowledge transfers.

---

## layout/

Structural blocks that define **arrangement and structure**.
Reusable, largely content-agnostic.

Subfolders (create as needed): `split/`, `grid/`, `carousel/`, `stack/`, `accordion/`.

## hero/

Page entry blocks that appear at the top of a page. High-impact, opinionated,
typically once per page.

## feature/

Storytelling and marketing-focused blocks. Purposeful, opinionated — when a
block exists to drive a message or action, it belongs here.

## utility/

Helper blocks (spacers, dividers, anchors, notices, CTA bars) that support
layout and editing rather than storytelling.

## misc/

Blocks that don't fit anywhere else. Use sparingly, and include a note
explaining why.

---

## How to Decide

- Structure or layout → `layout/`
- Page entry → `hero/`
- Storytelling / value → `feature/`
- Supports layout or editing → `utility/`
- Doesn't fit anywhere → `misc/` (with justification)

### Layout vs Feature

A block being CMS-controlled does **not** automatically make it `layout/`.

- `layout/` = **structural + content-agnostic** (a reusable pattern)
- `feature/` = **storytelling / conversion + opinionated** (a designed message)

**Quick test:** could this block be reused for a completely different purpose
without feeling weird? Yes → `layout/`. No → `feature/`.

## Block folder contents

Each block folder contains:

```
BlockName/
├── BlockName.tsx           React Server Component (or "use client" if needed)
├── BlockName.module.scss   Scoped styles
└── block.config.json       Metadata: title, description, keywords, requires
```

The manifest (`blocks/manifest.json`) is auto-generated by
`scripts/generate-blocks-manifest.ts` — do not edit by hand.

### block.config.json schema

```json
{
  "title": "Hero Page",
  "description": "Standard page hero with title and background image.",
  "keywords": ["hero", "header", "image"],
  "requires": ["gsap"]
}
```

`requires` is informational for now — future work: use it to dynamically load
client-side libraries only for blocks that need them.
